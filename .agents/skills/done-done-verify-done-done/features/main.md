# Main command

Part of the done-done verification map; reached at what README.md says a user runs first.

Source: `src/` (built to `dist/`), `skills/done-done/SKILL.md`, `integrations/firstmate/`, `package.json`, `package-lock.json`, `tsconfig.json`, `journeys/e2e.mjs`, `test/` and the landing page `docs/index.html`, which README.md mirrors. `done-done affected` maps a change to any of them to this feature's `e2e` journey.

## Sub-features

- Open/seal a native evidence run, check its captures, record a receipt and verify its caller HEAD.
- The [`look` step](../../../../docs/reference.md#look-check) a journey calls: the e2e journey's fixture repo runs `look-clipped` on `test/fixtures/look/clipped.html` (a card title clipped by its box), which must fail the run naming `h3.card-title`, and `look-fixed` on `test/fixtures/look/fixed.html`, which must pass; both captures must be 390x844 and are copied to the outer run folder as `<run-id>.look-clipped.png` and `<run-id>.look-fixed.png`. Needs Chrome or Chromium on PATH. Open both captures: the clipped title shows one line, the fixed one shows all of it.
- The [`lint` gate](../../../../docs/reference.md#lint-check): the e2e journey writes one claim whose evidence file exists (`lint` must print `PASS`, exit 0) and one that names a missing file (`FAIL: evidence file missing or empty: ...`, exit 1); the pass and fail transcripts are in the outer run's `<run-id>.log`. Needs no judge or network. Drive by hand: write a `## Checks` file and an evidence folder, run `done-done lint <file> <folder>`, then lint the same evidence from a file in another folder to see the reuse fail; each run is a row in `$DONE_DONE_HOME/lint.log`. Size rules `checks.upstream_catch_up` and `checks.moved_from` (off by default): the e2e journey drives a 1,100-line PR URL through a stand-in `gh` (200 lines already upstream, 300 moved from a sibling repo): `lint` must print `FAIL: 1100 added non-generated lines` with both off and `PASS` with either on, all in the outer run's `<run-id>.log`; `test/cli.test.mjs` covers the other-owner and no-moved-from-line cases. `checks.generated_paths` (default none): the e2e journey lints the same 1,100-line PR (one file, `lib/big.js`) with `generated_paths: ["lib/**"]` and must print `PASS`, and `FAIL: 1100 added non-generated lines` with the key unset or a glob (`gen/**`) that misses; `test/cli.test.mjs` covers it too.
- Agent calls that stop early: a streaming agent (pi, opencode, codex, `acp:<target>`) that prints nothing for 5 minutes is stopped, and a provider rate limit (HTTP 429, a usage limit) ends any call at its first line (except a claude judge call with images, which stops only at claude's own rejected rate-limit event; see [Agents](../../../../docs/reference.md#agents)). Both name the agent's stderr and, for a drive, the call record. Drive it with `agent: pi` and `agent_path_override.pi` set to a stand-in script that writes `Error: 429 weekly usage limit reached, resets at <time>` to stderr and keeps printing; run `done-done doctor --probe` and capture the output as `probe-429.txt`. It must finish in seconds with `probe,missing` naming the limit and its reset time. A stand-in that writes a warning and then sleeps must fail the probe after 30 seconds, with the warning in its reason and its fix line.
- First run: `init` says to commit `.done-done.yaml` and the verify skill before the first capture; a capture from a dirty tree fails `check` naming the fix; `status --run <id>` shows the evidence run record `run` printed (the e2e journey asserts it); `check` on a detached HEAD uses its commit as the claim id, so a fresh capture passes there; `init --journey` refuses an absolute path inside the repo and names the relative form (exit 2, nothing written). Drive: `node dist/cli.js init` in a fresh repo, `run`, `status --run`, `check`, and `init --journey smoke -- bash <abs path inside the repo>`. The integration tests in `test/cli.test.mjs` cover each.
- Judge setup: `init --judge` takes any agent and model, the coding agent's own too, and the judge kit installs with the tool; `doctor` reports the judge `missing` only until one is set, with the `init --judge` command. The integration tests in `test/cli.test.mjs` cover a same-agent judge and the doctor row. `init --judge` alone (no `--agent`, `--hook` or `--journey`) writes only the global config, in any directory; `judge.env_file` (global config) names a `KEY=value` file whose keys reach the judge's call when the shell has not exported them. Drive: `DONE_DONE_HOME=<temp> node dist/cli.js init --judge claude --judge-model claude-haiku-5-5` in a plain folder (no `.done-done.yaml`, no `.agents`), then `doctor` with `judge.route: openai:key` and `env_file` set and `OPENAI_API_KEY` unset (`OPENAI_API_KEY is set`). The integration test `init --judge alone changes only the global config` covers both.
- Claude judge sign-in: the `claude-code` judge runs your own `claude` with your normal sign-in, with no sign-in folder of done-done's, no `HOME` or `CLAUDE_CONFIG_DIR` override and no separate `auth login` step. Drive: with `agent_path_override.claude` set to a stub that records its env, `doctor` shows the judge `ok` with a claude binary alone, and `check` runs the stub with your `HOME` and no `CLAUDE_CONFIG_DIR`, `--safe-mode` and `--no-session-persistence`. A stub that reports not signed in stops the check with exit 2 naming `claude auth login`. A config that still has `judge.claude_code` loads normally, the key is ignored, and one line says to delete it. Integration coverage: the judge tests in `test/cli.test.mjs` (`judgeSetup`) and the doctor judge tests.
- Judge for one call: `check --judge <route>` (the form `judge.route` takes) judges that call with that route instead of the config's, saves nothing, and an unknown route is a usage error (exit 2). Drive: a throwaway `DONE_DONE_HOME` whose `judge.route` names a judge that cannot start, plus a stub gemini judge through `agent_path_override`; `check` fails (exit 2), `check --judge answerer:gemini` passes with `judge.route: answerer:gemini` and the config file unchanged. Integration coverage: test/cli.test.mjs (`check --judge picks the judge`).
- MiniMax judge route: `judge.route: minimax:key` (or `check --judge minimax:key`) judges on `MINIMAX_API_KEY` through the kit, at `MiniMax-M3.1-Flash-Preview` when `judge.model` is empty, and falls back to `claude-code` at claude's cheap model when its call fails (the only route with a fallback; the result's `judge.route` names the route that answered). Drive: a throwaway `DONE_DONE_HOME`, the key set for that one command from its file (never printed), `check --judge minimax:key --outcome <claim> <text capture>`; the result's `judge.route` is `minimax:key` and the capture passes. The integration test in `test/cli.test.mjs` covers the default model, the MiniMax-only key address and the fallback on a refused or missing key.
- [Real-product evidence](../../../../docs/reference.md#real-product-evidence): one model-free rule on a command's text marks a journey or run code-only when it only runs tests, typecheck, lint or a build (`npm test`, `yarn run check`, `tsc`, `pytest`), or a test or guard script by its file name or folder (`bash tests/x.test.sh`, `node scripts/floor-guard.mjs`; integration test `init refuses a journey that only runs a test or guard script ...` feeds the fleet audit's exact commands). `init --journey` refuses one (exit 2, nothing written) and init's verify skill refuses a code-only launch or drive; `check` and `receipt` stop before the judge (exit 2) when every journey is code-only or every cited capture comes from a code-only run; a receipt records `runs`, so `gate` and `receipt --verify` fail one whose runs are all code-only or missing; `doctor`'s last row, `real_product`, is a warning beside real journeys and `missing` (exit 2) when all are code-only. Drive: `done-done run e2e`; its fixture commits the receipt on a `gate` branch (`gate` prints `PASS`), then the same receipt with code-only runs (`FAIL: ... no real-product proof`), runs `init --journey check -- 'yarn run check > ...'` (refused), adds a `npm run check` journey (doctor `warning`, `check` of its log exits 2), then keeps only that journey (doctor `missing`, exit 2; `check` of a real capture exits 2 naming `check`). Prove: the outer run's `<run-id>.real-product.log` holds that transcript. Integration coverage: test/cli.test.mjs (`check and receipt refuse proof from code-only journeys`, the gate, doctor and verify-skill tests) and test/conformance.test.mjs (the README example).
- [Core journey and release path](../../../../docs/reference.md#core-journey-and-release-path): `doctor`'s required `core_journey` row is `missing` until a journey with `core: true` drives the product (or the verify skill's feature map marks a `(core journey)` entry), and `upgrade_journey` is `missing` when a tracked file shows an installable artifact (a non-private `package.json` with `bin`, an Android or Expo app, Python console scripts, a Rust `[[bin]]`, goreleaser, a systemd unit) and no `upgrade: true` journey or `(upgrade journey)` entry is named; `init --journey <name> --core|--upgrade` writes the flag, and init's verify skill refuses an answer with no core feature or, for such an app, no upgrade feature. Drive: `done-done run e2e`; its fixture drops `core: true` from `shots` and `doctor` exits 2 naming `core_journey` and the `--core` fix, then restores it and `doctor` names `journey shots is the core user journey`. Prove: those transcripts in the outer run's `<run-id>.log`. Integration coverage: test/cli.test.mjs (`doctor requires a named core journey ...` and `init has the agent name the core journey ...`).
- [Affected journeys](../../../../docs/reference.md#affected-journeys): `done-done affected [<base>]` reads the diff from the last receipt before HEAD (else the merge base with the default branch), maps each changed file to the journeys whose command runs it and to the features whose file cites it (and the journeys they name, or `verify --feature` for one that names none), adds the core journey when a file is in no feature or journey or there is no base, and exits 1 until a receipt for HEAD has a run of each; bare `done-done`, what the session hooks run, names those journeys too. Drive: `done-done run e2e`; its fixture is fresh at the receipted HEAD, then on a branch adds a feature file citing `src/app.js` (stale, needs `shots`), adds `src/billing.js` that no feature cites (flagged, core fallback), runs `shots` and records a receipt (fresh again). Prove: the outer run's `<run-id>.affected.log` holds that transcript. Dogfood: `done-done affected` in this repo lists `e2e` and `upgrade` for a release change. Integration coverage: test/cli.test.mjs (`affected maps a diff to journeys and features ...`, and the agent-drive verify test for a receipt's `feature`).
- [Step record](../../../../docs/reference.md#step-record): a journey (or agent drive) writes `steps.json` beside its captures with the target version, start state, user steps and end result; `run` and `verify` keep it in the run record (`steps`, `tool`), and `check`, `receipt`, `receipt --verify` and `gate` refuse a claim that no cited real run's record covers (a word match of the claim against the steps and result, no model), while a run recorded before step records passes with a `warnings` entry (`WARN:` after `PASS` in `gate`). Drive: `done-done run e2e`; its fixture runs a `wrapper` journey whose log and honest record say `ran the unit suite` and `check --outcome 'a user can attach to a pane and see its output'` exits 2 naming `attach, pane`, a `cli` journey whose record names `fixture-cli greet` and `check --outcome 'fixture-cli greet prints hello'` passes, then the same run with `tool` and `steps` deleted from its record passes with `warnings`. Prove: those transcripts in the outer run's `<run-id>.log`, and the outer run's own `steps.json` in the run record. Integration coverage: test/cli.test.mjs (`a claim needs a step record ...`, `receipt and gate carry the step record ...`).
- Check or receipt citations with [`--citation-base <dir>`](../../../../docs/reference.md#check-a-claim). The existing e2e journey covers a same-named wrong cwd file, omitted-flag compatibility, unchanged absolute citations, missing evidence rejection and unrecorded evidence rejection, plus execution of suggested receipt and remote gate commands.
- Verdict text for two failures: a `check --from <PR body>` that names evidence outside this checkout says it is not in this checkout and shows `--citation-base <dir>` first (re-capture advice only for files the run should have written under the evidence root); a `run <journey>` whose command exits non-zero names its first failing line in the reason, keeping the exit code. Drive: a Checks block naming a file that is not in the checkout, then a journey that prints `FAIL <test>` and exits 1. Prove: `help` leads with `--citation-base`, and `reason` reads `the run command exited 1: FAIL <test>`. Integration coverage: test/cli.test.mjs (the Checks-block file test and the `broken` run test).
- Named parts across captures: an outcome that names several parts (widths, themes or frames) needs each one shown by a passing capture, and the check matches those parts by name across the separate per-capture judge calls, so a call that lists them in another order or writes a label with other case, spacing or trailing punctuation still covers the same part; a part a reply names that no passing capture shows makes the check inconclusive and names it. Drive: with a real judge set (the cheapest model), `done-done check --outcome "the sent message shows at the bottom of the thread at 390 and 1440 wide" <run>/widths-390.json <run>/widths-1440.json`, then the same command with the 390 capture alone. Prove: the pair passes with every named part covered; the single capture exits 3 naming the uncovered width, and neither check invents a part. Integration coverage: test/cli.test.mjs (the names-two-widths, orders-and-writes and coverage-lists tests).
- Skill name prefix: every skill done-done writes is `done-done-*`; an older `verify-<app>` folder (no `skill:` set) is still read by every command, and `init` moves it once to `done-done-verify-<app>`, updates its `name:` line and prints `skill_renamed: <old> -> <new>`. The e2e journey drives it in a throwaway repo and the transcript in `<run-id>.log` shows the `init` output and the folder list. Integration coverage: test/cli.test.mjs (`init moves an older verify-<app> skill`).
- [Maintain reads what the skill names](../../../../docs/reference.md#keep-the-verify-skill-true): a tool-less reader (opencode, pi, acp) is sent every tracked file a feature file names, with or without a line (`public/index.html`), and `SKILL.md` too when it names source; a feature file that names none ends the run `blocked` (`coverage`), never `clean`; statements about done-done itself are not drift. Integration tests: `maintain gives a tool-less reader the source a feature file names without a line...` and `maintain reads SKILL.md too...` in `test/cli.test.mjs`. Drive on the real product: `done-done run create-maintain` (`journeys/create-maintain.mjs`, the walkthrough in [docs/example-create-maintain.md](../../../../docs/example-create-maintain.md) with a real agent, `DONE_DONE_JOURNEY_AGENT`/`DONE_DONE_JOURNEY_MODEL`, and the claude-code judge: init, source change, `maintain` drift, `auto_fix` fix, `maintain` clean, a browser journey, a judged `check`); save the `maintain` results and the judged screenshot. A pi rate limit shows the provider's message and reset time (integration test `a rate limit inside a pi JSON event...`).
- Init's verify skill: `init` has the agent the user set write `.agents/skills/done-done-verify-<app>` from the repo's own proof path; no agent set or an agent error writes no skill. Drive: build a small throwaway fixture repo whose `npm start` runs a real engine on the owner's home and whose `scripts/verify/drive.sh` runs a stub engine with a `mktemp -d` home, plus a `.done-done.yaml` journey that calls the script; commit it and run `DONE_DONE_HOME=<temp> node dist/cli.js init --agent pi --model <cheap model>` there, then `init` again in a copy with no agent set. Prove: `verify_skill: written by pi`; Launch runs `scripts/verify/drive.sh` with a `Safe:` line and warns off `npm start`; each Drive entry names a tracked source file; the no-agent copy reports `verify_skill: not written: no agent is set` and has no `.agents` folder. Integration coverage with a stub agent: test/cli.test.mjs (the `init ... verify skill` tests).
- [The sign-off handoff](../../../../docs/reference.md#send-a-run-to-sign-off): `signoff` writes the run's gate or evidence in the sign-off contract v1 shape and posts nothing; with the opt-in (`--post`, or `signoff.post: true` in `.done-done.yaml`) it posts that message to the board through `sign-off-axi`, records the card on the run (`status` shows it), and `--wait` brings the board's answer back to that same run. The board's gate vocabulary is the contract's: `approve` (Approve), `skip` (Skip the judge) and `fix` (Fix first), and a gate takes two or three of them, so a judge gate answers `fix` or `skip` and a spend gate `approve` or `skip`. Drive: in a throwaway repo, park a run at its gate (a judge that is unsure), then `done-done signoff` (nothing is posted, the message file is written), then `done-done signoff --post --board <a temporary board>`; serve that board and answer the card the way the browser does (`POST /api/answers`), then `done-done signoff --wait --run <id>`. Prove: the board file holds one card (`dd-gate-<run-id>`) with the run and its commit, `status --run <id>` shows `signoff.key`, and after the wait the run's `response.action` is the answer and its reason names the card; without the opt-in no board file exists at all. Integration coverage: test/cli.test.mjs (`signoff --post puts the run on the sign-off board and feeds the answer back to the run; without the opt-in nothing is posted`).

## Driving it with tmux/PTY

1. Launch the app as SKILL.md says and wait until it is ready.
2. Run `done-done run e2e` (or `node dist/cli.js run e2e`) from this repo. `journeys/e2e.mjs` drives a synthetic git repository and saves the transcript plus its capture into the outer run folder. To prove an installed tarball rather than local dist, set `DONE_DONE_TEST_CLI` to the absolute installed `done-done-axi/dist/cli.js` path. Use a private HOME, DONE_DONE_HOME and disk-backed TMPDIR. Every assertion must pass; the transcript prints each command, its output, exit code and the fixture HEAD.
3. Capture: save the output and exit status to $DONE_DONE_EVIDENCE_ROOT/main.txt, as SKILL.md's Evidence section says.
4. Stop what you started.

## Gotchas

See the [citation lookup contract](../../../../docs/reference.md#check-a-claim) rather than changing cwd or `evidence.root` to work around missing files. done-done gives no result without its judge, so the fixture repo sets a stub judge (deterministic, never a model) and a stub agent doctor finds but no step starts; a real judge is proven by a judged `check` with the agent and judge the user set. The fixture's look journeys embed this checkout's absolute path, so a local pre-commit hook that refuses home paths stops the fixture commit; run it with that hook off for the throwaway repo only (for example `GIT_CONFIG_GLOBAL=/dev/null`).
